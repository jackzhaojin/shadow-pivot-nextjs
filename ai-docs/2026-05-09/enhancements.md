# shadow-pivot-nextjs — Enhancement Assessment

**Date:** 2026-05-09
**Reviewer:** Claude (Opus 4.7)
**Branch reviewed:** `main` @ `ba914af` (last activity ~May 2025)

## TL;DR

The project is a `create-next-app` scaffold (Next 15.1.8 / React 19 / Tailwind 3 / App Router) with a `features/` layout, two routes (`/` boilerplate, `/tsla-dashboard` placeholder), and a working Azure Web App + GHCR pipeline. The deployment plumbing functions but has a real race-condition bug, the Dockerfile is naive, the only "feature" is unfinished, and there is no test or quality gate of any kind. Nothing is on fire — but if you wanted to bring it back to life, the list below is roughly what an hour-by-hour cleanup would look like.

**Legend**

- **Priority:** P0 (blocking/correctness), P1 (high impact), P2 (worth doing), P3 (polish)
- **Effort:** S (<1h), M (a few hours), L (1–2 days), XL (multi-day)

## P0 — Correctness & critical bugs

| # | Item | Effort | Notes |
|---|------|--------|-------|
| 1 | Fix race condition in `.github/workflows/main.yml` | S | `trigger-azure-steps` chains on `needs: trigger-build-and-push`, but `createWorkflowDispatch` only **queues** the build and returns immediately. The Azure restart fires before the new image is pushed, so the Web App pulls the *previous* `:latest`. Either delete this dispatcher entirely (the `main_shadow-pivot-nextjsv2.yml` push-triggered workflow already covers the same ground), or poll the dispatched run to completion. |
| 2 | Remove duplicate workflows | S | `main.yml` + `build-and-push.yml` + `azure-steps.yml` duplicate `main_shadow-pivot-nextjsv2.yml`. Keep one source of truth. |
| 3 | Delete dead `app/globals.css` | S | Identical copy of `styles/globals.css`, never imported. Layout imports `../styles/globals.css`. |

## P1 — High-impact production hygiene

| # | Item | Effort | Notes |
|---|------|--------|-------|
| 4 | Tag images by commit SHA, not just `:latest` | S | Push both `:latest` and `:${{ github.sha }}` to GHCR. Configure the Web App to pin a SHA (or have a "promote" job set it). Gives you real rollbacks instead of "rebuild an old commit." |
| 5 | Multi-stage Dockerfile + `output: "standalone"` | M | Current image ships full source + dev `node_modules` (`node:20-alpine` + `npm install` + `COPY . .`). Switch `next.config.ts` to `output: "standalone"`, multi-stage build (deps → build → runner), use `npm ci`, run as a non-root `USER`, add a `HEALTHCHECK`. Probably 3–5× smaller image and reproducible. |
| 6 | Add a PR quality gate workflow | M | New workflow on `pull_request`: `npm ci`, `npm run lint`, `tsc --noEmit`, `next build`. Today nothing prevents a broken main. |
| 7 | Pick a styling approach | S | `tsla-dashboard` uses CSS Modules; `home` uses Tailwind. Both are configured. Consolidate on Tailwind (it's already the default for the rest) so future contributors don't have to learn two systems. |
| 8 | Update page metadata | S | `app/layout.tsx` still has `title: "Create Next App"`, `description: "Generated by create next app"`. At minimum set the real product name; ideally per-route metadata. |
| 9 | Strip create-next-app boilerplate from `Home.tsx` | S | "Get started by editing app/page.tsx", Vercel deploy button, "Read our docs" links, Next/Vercel logos in `public/`. Replace with an actual landing page or redirect to `/tsla-dashboard`. |

## Suggested order if you wanted to "revive" this in a weekend

1. **Hour 1 (P0):** items 1, 2, 3 — clean the workflow mess and dead CSS.
2. **Hour 2–4 (P1):** items 4, 5, 6 — SHA-tagged images, real Dockerfile, PR gate.
3. **Hour 5 (P1):** items 7, 8, 9 — strip boilerplate, pick one styling system, fix metadata.
4. **Day 2 (P2):** item 10 — actually build the TSLA dashboard. Bring in #11, #12 alongside.
5. **Whenever:** P3 cleanup pass.

## Things I deliberately did NOT recommend

- **Migrating off Tailwind / off App Router / off `features/` layout** — all three are reasonable choices and changing them is churn for churn's sake.
- **Adopting a state manager (Redux/Zustand)** — there's no client state yet, don't pre-pick one.
- **Adding auth** — no use case in the codebase. If the dashboard becomes user-specific, revisit.
- **Switching off Azure Web Apps** — the deploy works; Container Apps / AKS would be over-engineering for one container.
